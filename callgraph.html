01

What the program is, and how it is put together

the 30-second answer

CraveFlow is a food delivery program that runs entirely in a terminal. One person signs in, and the program gives them the menu that matches their job: a customer orders, a restaurant manages its menu, a rider delivers, and an owner sees the reports. The whole program is 7 files and 91 functions, written with only Python's built-in tools — no libraries, nothing to install.

All the data lives in one dictionary called DATA, held in data.py. Every other file reads from it and writes to it. That is why the files are joined together: they all share the same dictionary, so an order placed by a customer appears instantly in the restaurant's list.

One burger, traced: what happens when you type F1001 4

verified against a real run

This is the question a panel actually asks: someone types something — where does the information go? Below is the complete path for Yajat ordering 4 Whoppers from Burger King. Nothing here is estimated. The keystrokes, the prompts, the arithmetic and the final bill all come from running the program.

The 5W1H rule is a way of describing a thing completely by answering six questions. Journalists invented it, and it works just as well on a program: if you can answer all six about CraveFlow, you understand it. Here they are, answered for the burger order — and this is the exact set of questions a viva panel works through.

What happened
Yajat ordered 4 Whoppers from Burger King. A new order O1004 was created with a total of Rs. 1155.00 and status PLACED.
Why it happened
He was signed in as yajat, who is a customer, so the program gave him the customer menu. He chose burgers, then Burger King, then typed F1001 4 — the ID of a Whopper and how many.
Who was involved
Yajat Sharma (customer), Burger King (restaurant), and 6 functions: choose_food, show_food_of, build_order, new_order_id, show_order, bill_lines.
Where it went
Into DATA["orders"]["O1004"] in data.py — a new dictionary holding who ordered, what, how many, from where, the total, and "PLACED".
When it happened
The moment he typed 0 to say "I'm done" — not when he typed the item. Items accumulate silently; the order is created once, at the end.
How it happened
choose_food() read the line, checked it against the restaurant and the sold-out flag, put {"F1001": 4} into a dictionary, then handed it to build_order(), which did the multiplication and wrote the order.

The nine steps, one keystroke at a time

Each step below is a real moment in the run above. The prompt is the exact text the program printed, and the function named is the one that was executing at that instant.

1

Sign in, and the role decides the menu

main.py → login(), welcome(), open_menu()

Yajat types his username and password. login() looks the name up in DATA["users"] and checks the password. Then open_menu() reads his role — "customer" — and hands him to customer_menu(). One person, one menu; nobody sees options they cannot use.

2

Choose a style of food

customer.py → pick_genre()

He picks 8, which is Burgers and Sandwiches. The list is not hard-coded: pick_genre() asks places_by_genre() which kitchens have food right now and groups them. Because only kitchens with available food are listed, he can never pick a kitchen that is sold out.

prompt: Your choice: 8 screen: -- Burgers and Sandwiches -------------------------------------------
3

The three burger kitchens are printed

customer.py → browse_one_genre()

Burger King, Subway and Grill Master appear as three boxes. The numbers on screen are the numbers the program accepts — that is the point of passing places down as a list. A kitchen whose food has all sold out never reaches this screen at all.

shows: Showing 13 items from 3 restaurants.
4

Pick the kitchen

customer.py → choose_food()

He types 1. The number is turned into a position — place = places[position - 1] — which is the kitchen burger_king. From here on, every dish must belong to that one kitchen, because a single order goes to a single kitchen.

prompt: Which restaurant? (0 to go back): 1 shows : 1. Burger King 2. Subway 3. Grill Master
5

Burger King's menu is printed on its own

customer.py → show_food_of(place)

Now only that kitchen's 5 dishes are shown, one row each. The row is built by food_line(), which hands the columns to design.columns() — that is why this table lines up exactly with the tables in every other screen.

rows: Whopper F1001 Rs. 280.00 ... and 4 more
6

Type F1001 4 — and nothing appears

customer.py → choose_food(), inside its while loop

This is the step that surprises people. The line is split into an ID and a count, put through all four checks, and stored in a plain dictionary called chosen. Nothing is printed, because the order does not exist yet. He is filling a basket, not placing an order. He types 0 when he is done — that is the moment the order is created.

prompt: Food: F1001 4 -- nothing prints, the line was accepted prompt: Food: 0 chosen = {"F1001": 4}
7

The bill is worked out

customer.py → build_order(username, place, chosen)

build_order() loops over the basket. For each dish it multiplies price by quantity and adds to a running total: 280 × 4 = 1120. Then it looks up Burger King's delivery fee (Rs. 35.00) and adds it. The sum is rounded with round() so a total never shows a long tail of decimals.

food_total: 280.0 * 4 = 1120.0 fee: 35.0 total: round(1120.0 + 35.0, 2) = 1155.0
8

The order is written into the dictionary

data.py → DATA["orders"]["O1004"]

A new ID is invented by new_order_id(), and one new dictionary is added to DATA["orders"] holding seven fields. This is the only moment the order comes into existence. Everything after this just moves the status field along.

"customer" = "yajat" "items" = ["F1001"] "quantities" = {"F1001": 4} "restaurant" = "burger_king" "total" = 1155.0 "status" = "PLACED" "rider" = None
9

The order screen prints the receipt-shaped box

customer.py → show_order(order_id) → bill_lines(order_id)

show_order() asks bill_lines() for the rows to print, so the order screen and the receipt can never disagree about the money. The count is written x4, and the three totals are stacked underneath. The customer now holds an ID — O1004 — which is the handle everything else uses.

prints: +- Order O1004 [PLACED] ----------------------------+ | Whopper x4 Rs. 1120.00 | | Food total Rs. 1120.00 | | Delivery fee Rs. 35.00 | | To pay Rs. 1155.00 | +--------------------------------------------------+ also : Ordered from Burger King - delivered to Yajat Sharma
The single most useful thing to say in a viva: "The order does not exist until he types 0. Everything before that is just a basket in a dictionary, held in memory. That is why nothing prints when he types an item — because nothing has been decided yet."

One pattern, used three times: the guard

the thing to point at

Three functions across two files ask the same question — which order do you mean? — and all three must refuse the wrong answer. Rather than repeat that refusal, each file has one helper that does the asking and the checking, and the actions stay short. 

# restaurant.py — the guard, written once
ask_order_id(username, action, allowed)

   open_orders = orders_with_status(username, allowed)
   if len(open_orders) == 0:
       warn("There is no order you can " + action + " right now.")
       return None              # nothing to act on

   show_orders(open_orders)     # only show what is allowed
   order_id = input("Which order to " + action + "? ").upper()

   if order_id not in DATA["orders"]:
       warn("No order found with the ID " + order_id + ".")
       return None

   if order_id not in open_orders:
       warn("You cannot " + action + " that order.")
       return None              # it exists, but not ours

   return order_id
The three actions that reuse the guard
ActionAllowed statusesResult
accept_order()["PLACED"]→ ACCEPTED
reject_order()["PLACED"]→ CANCELLED
cancel_order()["PLACED", "ACCEPTED"]→ CANCELLED
Why not put it in one shared file? The three actions live in restaurant.py and the rider's version lives in rider.py — they ask different questions, because a kitchen picks from its own orders while a rider picks from the shared queue. Two copies of a ten-line guard is cheaper than one shared helper that both files must import for a single call.
07

Why the program writes no files at all

the question that catches everyone

There is a function called save_data() and it is called from 14 places across the program. It does nothing, and that is on purpose.

The answer to give: "Saving is switched off on purpose so the demo always starts the same way. The function is still called everywhere it should be, so turning saving back on is a job of writing the body of one function. Nothing else has to change."

The consequence is that everything lives in memory for as long as the program runs. Close the terminal and the orders, menu edits and price changes are gone, and the next run starts from the same 29 kitchens and 143 dishes. For a demo that is the right behaviour, because the fourth run looks exactly like the first.

There is no import json anywhere in the program, and no open() call for writing. The only thing Python ever touches on disk is the .py files themselves. That is why the ledger at the top of this page reads 0 files written.

The one loop that runs the whole program

while True, and how it ends

There is no framework and no window to close. The program is one loop that keeps redrawing the menu until someone chooses to leave, and inside it a second, smaller trick: the menu only prints the one line that can change, so a long session does not scroll the answer off the screen. 

# the whole menu loop, in five lines of idea
while True:
    if it changed, say what changed
    show the heading and the choices
    ask for one choice
    if choice == "0": return          # the only way out
    else       : run that one action, then loop
